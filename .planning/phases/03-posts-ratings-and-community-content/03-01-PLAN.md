<mutation_authorization_matrix>
| Mutation or read | Guest | Authenticated unverified | Verified non-member | Verified member | Admin |
|---|---|---|---|---|---|
| Read public university posts/feed/discussions | allow | allow | allow | allow | allow |
| Create standalone post | deny 401 | deny 403 | allow when verified | allow when verified | follow underlying verification/owner rules; no extra moderation or bypass behavior |
| Reply/comment on existing post | deny 401 | allow; no membership check because none is specified by the SRS | allow | allow | follow underlying auth/verification/owner rules; replies do not require verified status |
| Edit own post | deny 401 | deny 403 (post edit requires owned post and does not imply standalone-post creation) | allow for owned post | allow for owned post | allow only for an owned post; admin role grants no edit ownership bypass |
| Edit another user's post | deny | deny | deny | deny | deny unless separately scoped moderation is implemented outside Phase 3 |
| Edit a comment | deny | deny | deny | deny | deny; comment editing is outside the SRS and Phase 3 scope |

This matrix preserves public reads from Phase 2 and applies existing database-backed verification and ownership rules. Membership is intentionally absent from standalone posts, replies, and reviews: the SRS requires verification for standalone posts/reviews but does not require a CommunityMembership row for those mutations. Admin moderation, deletion, and platform-management actions remain out of scope.
</mutation_authorization_matrix>

## Trust Boundaries

| Boundary | Description |
|---|---|
| Browser to Express API | Request body, slug, post IDs, comment IDs, and bearer tokens are untrusted. |
| Express services to PostgreSQL | Service code maps authenticated identity and validated relationships to Prisma writes. |
| Public feed response to browser | Response must not disclose email, auth identifiers, roles, or unrestricted relational data. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-03-01 | Elevation of privilege | post/comment mutation routes | high | mitigate | Resolve current User from Supabase identity, require verified status only for standalone posts, require auth for replies, and use req.user.id for ownership. |
| T-03-02 | Tampering | comment parent and university relationship | high | mitigate | Load post and parent comment together, require same post/university, reject mismatches, and cover guessed IDs in integration tests. |
| T-03-03 | Information disclosure | feed and discussion serializers | medium | mitigate | Select only public profile fields and post/comment fields; explicitly test absence of email, Supabase IDs, roles, and auth metadata. |
| T-03-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package install is planned; retain the package-legitimacy gate for any executor deviation. |
</threat_model>
